# Checklist automation status

This is the implementation update for the 400 line-item Electron checklist audit. The original audit's strict standard counts an item as autonomous only when the tool can finish its assessment without the tester logging in, providing an application-specific workflow or policy, or validating the result. Under that standard the earlier **6 autonomous / 156 assisted / 238 missing** baseline is not replaced by a new claimed pass rate: the new campaign needs a one-time test profile and a prepared app session, and no target app was provided for an end-to-end assessment. The six bounded software-version/advisory facts remain the only strictly autonomous items. This does not mean the other 394 require a manual action for every test; a configured run handles its cases without per-case prompts.

## Implemented in this iteration

| Capability | What the tool now does itself | Remaining setup or limit |
|---|---|---|
| Direct global inventory | Finds direct `window`/`globalThis` assignments, `Object.assign` and `Object.defineProperty` in scanned source, alongside contextBridge inventory. | Dynamic aliases and actual exposure to a particular origin remain unresolved. Checklist 02.04 receives supporting evidence, not a complete global inventory. |
| Document field campaign | Rebuilds a declared JSON/form save request, mutates up to eight named or automatically discovered string fields, saves, reopens/reloads, records a distinct field/case signal, then attempts restoration. | Supply a disposable record, precise save/view workflow and prepared test account. Automatic selection is bounded and cannot infer business semantics. Capture mode needs one seed save. |
| Executable probes | Tests script tag, event handler, SVG handler and clicked `javascript:` link, plus Node/Electron presence, a read of a random tool-owned file canary, and `eval` in the document page. | A signal proves execution on the observed route only. No signal is *not observed*, never a safe verdict. Page API calls need an explicit benign contract. |
| JSON and resource cases | Mutates null, boolean, number, array, object, empty and bounded long values; uses loopback image, SVG, script, frame, stylesheet, font, media and image redirect fixtures. Records receiver requests and only the presence of credential headers. | String-field discovery is bounded to eight; no complete schema mapping, response readability, private-network reachability beyond loopback, or native/server process attribution. |
| Optional page API cases | Uses one declared page method with a baseline and bounded argument variants, including type and path/URL strings. The loopback URL variant verifies a receiver request. Reports call and promise outcome without logging returned data. | Invocation/resolution is not evidence that IPC accepted it or a privileged side effect happened. A normal call can have app-specific side effects, so use a disposable method/record. |
| DOCX import | Generates six bounded ZIP/Office XML fixtures and posts them as multipart form data to a configured import route. Records acceptance, view attempt and loopback external-relationship request. | No generic proof of conversion, rendered output, parser safety or cleanup of documents the import API creates. |
| Navigation links | Clicks three configured document links (loopback, redirect, data URL) and records Electron URL change and receiver requests. | Does not establish OS-browser handling, all origins/schemes, popup policy or deep-link behavior. |
| Coverage and cleanup | Reports accepted/rejected/failed saves separately from view and execution, flags missing campaign startup, notes restoration failures, deletes the tool's canary and closes the receiver. | Existing app state or extra side effects of the declared save method cannot be reset generically. |

The current default profile selects **28** field cases. There are **42** field cases available, including 11 optional page-API and three optional navigation cases, plus six opt-in DOCX fixtures. These are variants, not completed checklist items. One can run end-to-end only when its exact save/view or import profile works in a real app. The earlier row estimate of 6 autonomous, 199 assisted and 195 missing predates the multi-field, data-canary, DOCX and navigation additions; it has not been formally rescored or validated against a target app. The strict autonomous count does not increase from adding a campaign that needs app-specific setup.

## What remains manual, and what to automate next

One-time app-specific setup remains: a test account/session, a disposable document, its save request and field, the saved view, any benign exposed API contract, and the trust policy for approved origins and capabilities. Human review is still needed where the application has an unknown workflow or business rule, or when a finding needs a cross-account or privileged-effect conclusion. No person needs to approve each of the configured campaign cases.

The new multi-field, DOCX and navigation mechanics remain bounded: they do not discover every app-specific route, parse the target's conversion output, or reset documents created by an import. Large remaining campaigns include real Windows/Word/file-association observations; full popup/deep-link and origin matrices; renderer access to another account's data and authenticated canaries; and complete IPC sender/argument/side-effect verification. These can be automated after test fixtures and contracts are supplied, but a generic scanner cannot invent a customer's authorization policy, isolate a second account, or infer whether a privileged business action is allowed. The next useful target-app regression is the historical scan's document-to-`file-open-docx`/`shell.openPath` path, followed by `auth-get-creds` and `open-url` from a proven document renderer. The historical scan alone cannot run those tests: it lacks a runnable app and test account.

Run a profile with `electronegativity --app ./my-app --campaign docs/campaign.example.json --out test-results`, after replacing the example URLs/body with a disposable workflow. The ordinary report and diagnostics keep delivery, rendering and execution distinct. A tool-generated `javascript:` link is clicked only when its configured saved view contains the link; the tool does not inject code into the page to claim the document executed it.
